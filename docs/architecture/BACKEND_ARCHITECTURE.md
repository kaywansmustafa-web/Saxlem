# Saxlem Backend Architecture

## Decision

Saxlem uses one NestJS modular monolith in `backend/`, one PostgreSQL database,
Prisma migrations, REST under `/api/v1`, and OpenAPI contracts. Modules may be
split only after measured scaling, reliability, ownership, or deployment needs.
Microservices, gateways, brokers, event sourcing, and a CQRS framework are not
part of the foundation.

## Dependency direction

Each future business module follows domain → application → infrastructure and
presentation adapters. Controllers call application services. Prisma records do
not cross infrastructure boundaries. Cross-module work uses exported application
contracts rather than importing another module's repository implementation.

Reserved modules are Identity, Organizations, Clinics, Clinic Staff, Doctors,
Patients, Patient Profiles, Appointments, Doctor Availability, Queue Sessions,
Notifications, and Audit. Sprint 13A provides boundaries only; it implements no
feature endpoint or workflow.

## Tenancy

Tenant-owned records carry `organization_id`; clinic operations also carry
`clinic_id`. Authentication will establish a principal, request context will
resolve a tenant selection, authorization will validate membership/capability,
and repositories must scope every query. Composite clinic foreign keys prevent
cross-organization references. Tenant-escape integration tests are mandatory
before production. PostgreSQL RLS remains optional defense in depth, never the
sole boundary.

## Identifiers and time

Prisma 7.8 supports `uuid(7)` cleanly, so UUIDv7 is generated by Prisma clients.
The database migration intentionally does not depend on a PostgreSQL-native
UUIDv7 function. Writes outside Prisma must supply valid UUIDs. If a future stack
cannot preserve UUIDv7 safely, random UUIDv4 is the approved non-blocking fallback.
Timestamps are UTC; clinics store an IANA timezone for human scheduling.

## Transactions

Future contested queue commands must claim an idempotency key, lock the queue
aggregate, validate its expected version and transition, update records, append
audit/outbox entries, and commit atomically. REST/database snapshots remain the
authority. Event delivery never becomes the source of state.

## Realtime direction

Server-Sent Events are the preferred first transport for low-frequency,
server-to-client updates. SSE will carry minimal versioned invalidation events;
clients refetch REST snapshots after reconnects or version gaps. A Flutter
reconnect spike is required before implementation. Sprint 13A implements no SSE.
